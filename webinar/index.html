Governing Enterprise Multi-Agent Systems on Google Cloud

A Replicable Reference Architecture with Vertex AI Agent Engine, A2A Protocol, and Apigee X

Welcome, everyone. Today we are going to look at what it actually takes to run a multi-agent AI system in production on Google Cloud. Most demos you see in the AI space are built inside a single project, running on a developer's desktop, using personal API keys and direct internet connections. That is great for prototyping, but it is not how enterprise software works. In the real world, you have strict network boundaries, identity requirements, token budgets, and audit mandates. What we are presenting today is not a toy or an idealized conceptual diagram. It is a complete, working reference implementation that spans three separate Google Cloud projects, governs every single model and tool interaction through Apigee, traces every hop from browser to database with a single correlation ID, and can be rebuilt from scratch with a single set of declarative manifests. Let's dive in.
Situation

Single-model chatbots are evolving into coordinated multi-agent networks

1. Workflow Decomposition

Moving from monolithic, single-prompt chatbots to supervisor agents that orchestrate domain specialists.

2. Autonomous Action

Specialists interact directly with business systems through the Model Context Protocol (MCP) and REST APIs.

3. Distributed Operations

Transactions span multiple microservices, relational databases, and distinct operational boundaries.

Over the past two years, enterprise AI has moved through its first phase, which was mostly chatbots and single-prompt assistants. Today, organizations are building multi-agent systems where a coordinator or supervisor agent delegates specialized tasks to domain-specific agents—like an order specialist, a customer profile specialist, or a product catalog specialist. These agents don't just generate text; they interact directly with real-world databases and microservices through the Model Context Protocol. But as soon as you connect autonomous agents to production line-of-business systems, the architecture changes completely. You are no longer managing a simple request-response API. You are orchestrating a distributed system of semi-autonomous entities that negotiate tasks, execute transactions, and consume expensive LLM tokens at high velocity.
Situation

Google Cloud provides the core building blocks for enterprise multi-agent architectures

Agent Engine

Managed Vertex AI Reasoning Engines running ADK agents with built-in scaling.

A2A Protocol

Standardized protocol for agent discovery, skill cards, and token streaming.

Apigee X

Enterprise gateway for token quotas, developer keys, and policy enforcement.

The good news is that we don't need to invent new foundational infrastructure to run these systems. Google Cloud already provides the core primitives we need. Vertex AI Agent Engine gives us a fully managed serverless runtime for reasoning engines, built on the Agent Development Kit. The Agent-to-Agent, or A2A, protocol gives us a standardized communication and capability negotiation standard between supervisor and sub-agents. Cloud Run and Cloud SQL provide scalable, secure compute and relational persistence for our business logic. And Apigee provides the enterprise API management layer that has governed mission-critical traffic for decades. The components are all mature and available today. The real challenge is not whether these individual pieces exist, but how to wire them together into a secure, governed, and operable production topology.
Complication · Governance & Trust

Unmanaged agent deployments create ungoverned model access and untracked token spend

Shadow LLMs & Broad Credentials

  • Agents invoke foundational models directly using static service account keys.
  • No per-user identity enforcement at the model perimeter.
  • No capability to revoke access for one user without breaking the entire agent.

Zero Cost Attribution

  • Cannot answer: "Who spent the tokens, on which model, through which agent?"
  • Token consumption is unmetered until the monthly cloud invoice arrives.
  • Answering basic billing questions requires building custom log pipelines.
When teams rush an agent proof-of-concept into production, the first wall they hit is governance and financial control. In typical setups, agents call Vertex AI or third-party models directly using broad service account credentials or static API keys embedded in environment variables. There is no per-user identity check at the model boundary, no concept of token quotas, and no way to revoke access for a single user without breaking the entire agent. When the monthly cloud bill arrives, nobody can answer basic accounting questions: Who spent fifty thousand dollars on Gemini 1.5 Pro this week? Which agent generated those tokens? Was it the order specialist or the supervisor? Without an intermediary governance gateway, answering these questions requires building and maintaining an expensive custom data pipeline just to parse and correlate raw infrastructure logs.
Complication · Governance & Trust

Multi-hop agent delegations turn production transactions into opaque black boxes

Browser ➔ BFF ➔ Supervisor ➔ Specialist ➔ MCP Gateway ➔ Cloud Run ➔ Cloud SQL

Where did the 12-second latency spike or 500 error actually occur?

Disparate Silos

Logs scattered across multiple GCP projects and service boundaries.

No Shared Clock

Timing metrics formatted differently with inconsistent epoch precision.

Broken Trace Context

Traceparent lost during A2A handoffs or MCP tool invocations.

The second major operational blocker is opacity. In a multi-agent architecture, a single user query might trigger a cascade of operations: the supervisor inspects the prompt, calls a model, delegates over A2A to the order agent, which calls another model, invokes an MCP tool, which hits an internal microservice, which executes a SQL query on a database. If that request takes twelve seconds to complete, or fails with a 500 error, where did the breakdown happen? Was it model latency, a slow database query, a networking timeout, or agent orchestration overhead? In standard architectures, these logs are scattered across different services and different projects with completely different formats and no common correlation identifier. Debugging a failed transaction feels like searching for a needle in four separate haystacks.
Complication · Security Reality

Standard agent prototypes introduce critical identity, network, and database vulnerabilities

Spoofable Identity Headers

Prototypes trust raw incoming HTTP headers (e.g. X-User-Email) instead of cryptographically verifying signed JWT tokens.

God-Mode Service Accounts

All agents share a single over-privileged service account with unrestricted cross-project access.

Publicly Exposed Backends

Internal microservices accept public traffic, relying solely on simple API keys at the perimeter.

Static Database Secrets

Database passwords passed in plaintext environment variables rather than using IAM database authentication.

From a security perspective, agent prototypes frequently make dangerous compromises to get things working. They trust spoofable identity headers like X-User-Email sent from the browser instead of cryptographically verifying signed JWT tokens. They give every agent a single shared service account with broad admin privileges instead of enforcing least privilege. They expose internal backend microservices directly to the public internet because cross-VPC networking feels too complex. And they embed database passwords directly into runtime environment variables. In an enterprise environment, any single one of these vulnerabilities is an immediate security block. An enterprise agent architecture must guarantee that backend services have zero public surface, identity is cryptographically proven, and credentials like database passwords do not exist at all.
Complication · Engineering Reality

Brittle agent coupling and unrepeatable environments stall production operations

Brittle Coupling

Vertex AI produces a new engine ID per deploy. Hardcoded IDs mean redeploying a specialist breaks the supervisor.

Configuration Drift

Manual console clicks and hardcoded project IDs cause builds to work in one project but fail in the next.

Undocumented Edges

A2A token streaming under ADK 2.3 and bidirectional Private Service Connect lack working production reference implementations.

Finally, there is the engineering reality of running these stacks day-to-day. In Vertex AI Agent Engine, every deployment produces a new engine resource ID. If your supervisor hardcodes the specialist's engine ID, redeploying a specialist instantly breaks your supervisor. Furthermore, setting up the necessary infrastructure—cross-project Private Service Connect, IAM database authentication, DNS peering, and API proxies—involves dozens of interdependent steps. When done manually through the Cloud Console, you get configuration drift, hardcoded project IDs in scripts, and environments that cannot be replicated. When you look for documentation on the hard problems—like streaming tokens through A2A under ADK 2.3 or handling bidirectional Private Service Connect between Apigee and Cloud Run—the standard documentation runs out. Teams spend months rediscovering solutions to these exact integration traps.
The Core Architectural Question

“Can you build a multi-agent system where EVERY call—model, tool, agent, and business API—is governed, attributed, traced, and private… and the whole stack rebuilds from three empty projects?”

This brings us to the central question of today's webinar: Can you build a multi-agent system where every single call—whether it is a model invocation, an MCP tool execution, an inter-agent delegation, or a backend business API request—is strictly governed, attributed to a verified user, traced under a single ID, and kept completely private… and where the entire multi-project infrastructure can be cleanly rebuilt from scratch using automated, declarative tools? The answer is yes. And for the rest of this session, we are going to walk through the exact architecture, code, and mechanisms of the reference implementation that proves it.
Architecture · Topology

Three projects enforce strict separation of concerns across AI, governance, and data

AI Project (ai)

  • 4 Agent Engines (Supervisor + 3 Specialists)
  • BFF Cloud Run behind IAP
  • Firestore ACL & Secret Manager
  • Single-Pane Telemetry Sink

Apigee Project (gateway)

  • Apigee X Organization (7 Proxies)
  • API Products & Token Quotas
  • Per-User / Per-Agent Apps & Keys
  • Token Minting SAs (Access & ID tokens)

Backend Project (backend)

  • 3 FastAPI Microservices (Cloud Run)
  • Cloud SQL MySQL (IAM DB Auth)
  • Regional Internal Load Balancer
  • PSC Service Attachment to Apigee
Here is the architectural anchor of the entire system. We split the architecture across three distinct Google Cloud projects, each with a single, clear responsibility. In the Apigee project, we run the Apigee X organization. It is the governance plane: it holds the API proxies, defines token quota policies, and manages developer credentials. In the AI project, we run our four Agent Engines on Vertex AI, the FastAPI Backend-for-Frontend, our Firestore authorization database, and our centralized telemetry sink. In the Backend project, we host our core business system—three microservices and a Cloud SQL database behind an internal load balancer. The AI project has zero direct network connectivity to the backend project. Every single interaction between agents and backend services is forced to route through the Apigee governance gateway over private Google Cloud backbone networking.
Governance Plane

Apigee acts as the single governance gateway across models, tools, and backend APIs

Let's examine how Apigee functions as the central nervous system of this architecture. We deploy seven dedicated API proxy bundles. The `/ai-agents` proxy fronts the supervisor engine, translating external client queries into authenticated Vertex AI Reasoning Engine requests. The `/aiplatform` proxy fronts all model calls originating from the agents. The `/llm-stream` proxy provides a unified SSE streaming endpoint for direct user-to-model chat, routing requests dynamically to either Google Gemini or Anthropic Claude while applying identical security and quota policies to both. The `/mcp` proxy provides a managed gateway for tool discovery and execution. And the three e-commerce management proxies front the backend microservices, minting short-lived Google ID tokens to authenticate across the private internal load balancer. Every data path is governed in one place.
Governance Plane

Per-user API keys bound to IAP identities enforce token quotas before model execution

Key-to-Identity Binding

VerifyAPIKey validates that the key's owner_email matches the verified IAP email. Stolen keys are immediately rejected with 403.

Edge Token Quotas

LLMTokenQuota enforces rate limits before model invocation: 100k tokens/hour per agent, 10k tokens/5min per user.

Dual-Publisher Support

Gemini and Claude routed seamlessly behind the same gateway endpoint, governed under identical security and budgeting rules.

Here is how we solve the ungoverned access problem. When a user interacts with the system, they provide their personal API key. When that request hits Apigee, the gateway does not just check if the key is valid. It verifies that the `owner_email` metadata attached to the key matches the cryptographically verified user identity passed from IAP. If someone steals your API key, they cannot use it because their authenticated email will not match the key's owner. Furthermore, Apigee enforces native LLM token quotas at the edge before the request ever reaches Vertex AI. We enforce a 100k token-per-hour quota on agent applications and a 10k token-per-5-minute quota on individual users. If a rogue agent loops or a user exceeds their quota, Apigee rejects the call at the edge, protecting both your budget and your backend.
AI Plane · Agents

Domain specialists encapsulate scoped MCP toolsets under least-privilege service accounts

order_agent

Identity: a2a-order-sa

Tools: 6 scoped MCP tools (listOrders, createOrder, getOrderById, etc.)

Secret: apigee-key-order

product_agent

Identity: a2a-product-sa

Tools: Scoped catalog search, product detail, and inventory queries.

Secret: apigee-key-product

customer_agent

Identity: a2a-customer-sa

Tools: Scoped account lookup, address verification, and profile management.

Secret: apigee-key-customer

Rather than building a single monolithic agent with dozens of tools, we divide domain capabilities into three specialized agents: `order_agent`, `product_agent`, and `customer_agent`. Each specialist runs as an independent Reasoning Engine in Vertex AI, operates under its own dedicated service account, and holds its own unique Apigee API key stored securely in Secret Manager. Crucially, each specialist is provisioned with only the subset of MCP tools required for its domain. The order agent cannot see customer account tools, and the product agent cannot execute order modifications. By keeping each agent's tool surface small and focused, we eliminate tool selection ambiguity for the LLM and enforce least-privilege security boundaries at the agent level.
AI Plane · Agents

The supervisor coordinates over A2A with token streaming and dynamic self-healing discovery

A2A Token Streaming (ADK 2.3)

  • RemoteA2aAgent proxies with streaming client factory.
  • Tokens stream in real time as specialists generate them.
  • UI reveals delegation the instant transfer_to_agent emits.

Registry Self-Healing (~60s TTL)

  • Specialists auto-register in Agent Registry upon deployment.
  • Supervisor refreshes cache every 60s via before_agent_callback.
  • Specialists redeploy cleanly with zero supervisor redeployments.
Inter-agent communication is built on Google's Agent-to-Agent protocol. The supervisor connects to specialists using streaming `RemoteA2aAgent` proxies under ADK 2.3. As the specialist generates tokens, they stream immediately back through the supervisor to the frontend, revealing delegations the instant they occur. Even more importantly, we solved the brittle engine coupling problem through dynamic registry self-healing. When a specialist is redeployed, Vertex AI registers the new engine in Agent Registry. In the supervisor, a lightweight `before_agent_callback` inspects the registry on a 60-second TTL cache. When it detects a new generation of a specialist, it updates the in-memory proxy URL on the fly. You can redeploy specialists continuously throughout the day without ever restarting or redeploying the supervisor.
AI Plane · Security

Dynamic, Firestore-backed ACLs enforce fail-closed authorization per conversation turn

Turn-Level Evaluation

Evaluated on every query in before_agent_callback using the verified IAP identity. Instant permission revocation.

Fail-Closed Safety Net

Missing user record = zero agent access. before_tool_callback provides an unbypassable execution barrier.

Live UI Administration

Administrators manage roles and user-agent bindings directly in the Admin UI without modifying code or redeploying.

To control who can use which agents, we implemented a dynamic, fail-closed access control system backed by Firestore. On every single conversation turn, the supervisor extracts the verified user email from the invocation context and queries Firestore for that user's authorized agent list. If an employee is only permitted to access the product catalog, the supervisor dynamically removes the order and customer specialists from its available sub-agents for that request. If no record exists for a user, the system fails closed and denies all agent delegations. As an additional layer of defense, a `before_tool_callback` acts as a hard block if a restricted agent is somehow invoked. Administrators can update permissions in real time through the web UI, taking effect instantly on the very next turn.
Security & Networking

The entire data path is private by construction with Private Service Connect and IAM database auth

Verified IAP Identity

Cloud Run BFF verifies cryptographic signature of X-Goog-IAP-JWT-Assertion. Spoofable plaintext headers are ignored.

Bidirectional PSC

Northbound (AI ➔ Apigee) and Southbound (Apigee ➔ Backend) cross-project traffic routes strictly over Google private backbone.

IAM-Only Services

Backend Cloud Run services require Google ID token authentication; only Apigee's dedicated invoker SA is authorized.

Passwordless Cloud SQL

Cloud SQL MySQL uses IAM database auth. The runtime service account ecommerce-sa IS the database user. Zero DB passwords.

Security in this demo is enforced at the network and identity layers simultaneously. At the edge, Cloud Run sits behind Identity-Aware Proxy. The BFF verifies the cryptographic signature and audience of the `X-Goog-IAP-JWT-Assertion` header, completely ignoring untrusted headers. Across project boundaries, all traffic flows over Google's private backbone via Private Service Connect in both directions. The backend microservices on Cloud Run are configured with IAM authentication, accepting traffic only from Apigee's dedicated invoker service account. And at the data layer, Cloud SQL uses Cloud SQL IAM Database Authentication. The runtime service account `ecommerce-sa` is itself the MySQL user. There are no database passwords stored in code, configuration, or environment variables anywhere in the entire stack.
Observability · Logging

A single traceparent correlates every hop from browser to database across four named logs

Log Name Written By One Entry Per Key Telemetry Fields
front-ai-logs BFF Cloud Run UI Turn user, view, userMessage, latency_metrics, error
agent-ai-logs Agent Engines Engine Record engine, agent, session_id, model_call tokens, tool_call
apigee-ai-logs 7 Apigee Proxies Gateway Hit user, app, model, promptTokens, quotaRemaining, 4 timestamps
services-ai-logs Microservices HTTP Request service, verb, path, status, latencyMs

All logs reside in the AI project on a single canonical schema: event, component, traceparent, latency_metrics.

To solve the multi-agent opacity challenge, we established end-to-end W3C distributed tracing. When a user sends a message, the BFF mints a standard W3C `traceparent`. That header is passed downstream to Apigee, injected into Agent Engine sessions, forwarded across A2A metadata to specialists, transmitted to the MCP server, and delivered to the backend microservices. Every single component emits structured telemetry into one of four dedicated log streams in the AI project: `front-ai-logs`, `agent-ai-logs`, `apigee-ai-logs`, and `services-ai-logs`. Because all four logs adhere to a single canonical JSON schema with standardized latency metrics, filtering by a single trace ID in Cloud Logging reveals the exact, nanosecond-accurate timeline of a request across all three projects.

Tooling & Replicability

One environment file and three declarative manifests drive automated convergence

Declarative State

  • demo-environment.yaml (Single source of project IDs, regions, admin identity)
  • agents/runtime-manifest.yaml (Agent infra, SAs, ACL seed)
  • apigee/provision/manifest.yaml (Products, quotas, keys)
  • services/services-manifest.yaml (VPC, Cloud SQL, ALB)

Consistent CLI Grammar

CommandAction
tool --checkRead-only drift report
tool --dry-runPreview planned writes
tool (bare)Report ➔ interactive confirm
tool --applyNon-interactive CI apply
How do you ensure an architecture this sophisticated can be deployed reliably without human error? We built a declarative, manifest-driven tooling system. The entire deployment is parameterized by a single environment file, `demo-environment.yaml`, which specifies your project IDs, regions, and admin identity. Three version-controlled YAML manifests declare the desired state for the AI plane, the Apigee gateway, and the backend services. Seven core Python and shell tools converge the live cloud state to match the manifests. Every tool implements the exact same CLI grammar: `--check` inspects live state and outputs a drift report, `--dry-run` previews actions safely, bare execution prompts for interactive confirmation, and `--apply` executes non-interactive reconciliation for CI/CD pipelines.
Tooling & Quality

Automated guardrail tests fail the build on hardcoded IDs, documentation drift, and contract mismatches

Zero Hardcoded IDs

test_demo_env.py and test_docs_guard.py scan all manifests and docs, failing if literal project IDs/numbers appear.

Manifest Consistency

test_manifest_consistency.py validates cross-manifest contracts: SA names, secret accessors, audiences, and target servers.

Offline CI Execution

The entire pytest tests/ suite runs in seconds without requiring active GCP credentials or live cloud connections.

To guarantee that this repository remains clean and replicable over time, we enforce automated guard tests in `pytest`. One suite scans every manifest, configuration file, and markdown document in the repository, instantly failing the build if a developer accidentally commits a hardcoded project ID, project number, or internal email. Another test suite cross-checks our manifests against each other, verifying that the service account created in the AI manifest matches the invoker permissions in the backend manifest and the proxy bundle audiences in the Apigee manifest. These tests run completely offline without needing GCP credentials, ensuring that configuration drift is caught before code ever reaches a deployment pipeline.
