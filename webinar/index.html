Governing Enterprise Multi-Agent Systems on Google Cloud

A replicable reference architecture with the Gemini Enterprise Agent Platform (GEAP), the A2A protocol, and Apigee X

Repo  adk-apigee-multiagent-demo Format  40 min + 2 live demos License  Apache 2.0
Welcome, everyone. Today we are going to look at what it actually takes to run a multi-agent AI system in production on Google Cloud. Most demos in the AI space are built inside a single project, on a developer's desktop, with personal API keys and direct internet connections. That is great for prototyping, but it is not how enterprise software works. In the real world you have strict network boundaries, identity requirements, token budgets, and audit mandates. What we present today is not a toy or a conceptual diagram. It is a complete, working reference implementation that spans three separate Google Cloud projects, governs every model and tool interaction through Apigee, traces every hop from browser to database with a single correlation ID, and rebuilds from scratch with declarative manifests. Everything is open source. Let's dive in.
Situation

Single-model chatbots are evolving into coordinated multi-agent networks

🧭Workflow decomposition

Monolithic, single-prompt chatbots are giving way to supervisor agents that orchestrate domain specialists.

⚙️Autonomous action

Specialists act on real business systems through the Model Context Protocol (MCP) and REST APIs — they don't just generate text.

🌐Distributed operations

A single question fans out across engines, microservices, and databases — crossing real operational boundaries.

Over the past two years, enterprise AI has moved through its first phase — mostly chatbots and single-prompt assistants. Today, organizations are building multi-agent systems where a supervisor delegates specialized tasks to domain-specific agents: an order specialist, a customer profile specialist, a product catalog specialist. These agents don't just generate text; they interact with real databases and microservices through the Model Context Protocol. And as soon as you connect autonomous agents to production line-of-business systems, the architecture changes completely. You are no longer managing a simple request-response API. You are orchestrating a distributed system of semi-autonomous entities that negotiate tasks, execute transactions, and consume expensive LLM tokens at high velocity.
Situation

Google Cloud already ships the building blocks — the challenge is the wiring

🤖GEAP Agent Engine

Managed runtime for ADK agents on the Gemini Enterprise Agent Platform (formerly Vertex AI): sessions, scaling, registry.

🔁A2A Protocol

Standard for agent discovery, capability cards, and token streaming between supervisor and specialists.

🛡️Apigee X

The enterprise gateway: keys, quotas, analytics, policy — proven on mission-critical API traffic.

🗄️Cloud Run + SQL

Serverless business services and managed MySQL, connected privately via Private Service Connect.

Every component is mature and available today. What's missing is a governed, replicable topology that ties them together.

The good news is that we don't need to invent new infrastructure. Google Cloud already provides the core primitives. The Gemini Enterprise Agent Platform — GEAP, which many of you will know by its former name, Vertex AI — gives us Agent Engine, a fully managed serverless runtime for reasoning engines built on the Agent Development Kit. The Agent-to-Agent protocol, A2A, standardizes communication and capability negotiation between supervisors and sub-agents. Cloud Run and Cloud SQL provide scalable, secure compute and relational persistence. And Apigee provides the API management layer that has governed mission-critical traffic for decades. The components are all mature and available today. The real challenge is not whether the pieces exist — it is how to wire them into a secure, governed, operable production topology. That wiring is exactly what this session is about.

Complication · Governance & Trust

Ungoverned model access, and nobody can say who spent the tokens

🕳️Shadow LLMs on broad credentials

  • Agents call models directly on static service-account keys.
  • No per-user identity at the model perimeter, no quotas.
  • Revoking one user means breaking the whole agent.

🧾Zero cost attribution

  • "Who spent the tokens, on which model, through which agent?" — unanswerable.
  • Spend is invisible until the monthly invoice lands.
  • Answering it means building a custom log pipeline.
When teams push an agent proof-of-concept toward production, the first wall is governance and financial control. In typical setups, agents call Vertex or third-party models directly using broad service-account credentials or static API keys in environment variables. There is no per-user identity check at the model boundary, no concept of token quotas, and no way to revoke a single user without breaking the entire agent. Then the monthly bill arrives and nobody can answer basic accounting questions: who spent fifty thousand dollars on model calls this week? Which agent generated those tokens — the order specialist or the supervisor? Which end user drove that load? Without a governance gateway in the path, answering those questions requires building and maintaining a custom pipeline just to parse and correlate raw infrastructure logs.
Complication · Governance & Trust

Multi-hop delegation turns every transaction into a black box

Browser→ BFF→ Supervisor→ Specialist→ MCP→ Cloud Run→ Cloud SQL

Where did the 12-second latency spike — or the 500 — actually happen?

🗂️Disparate silos

Logs scattered across projects and service boundaries, each in its own format.

⏱️No shared clock

Latency metrics with different shapes and inconsistent precision — nothing adds up.

✂️Broken trace context

The traceparent gets dropped at A2A handoffs and MCP tool calls.

The second blocker is opacity. In a multi-agent architecture, one user query triggers a cascade: the supervisor inspects the prompt, calls a model, delegates over A2A to the order agent, which calls another model, invokes an MCP tool, which hits an internal microservice, which runs a SQL query. If that request takes twelve seconds or fails with a 500, where did it break? Was it model latency, a slow query, a network timeout, or orchestration overhead? In standard architectures those logs are scattered across different services and projects, in different formats, with no common correlation identifier — and the trace context that would tie them together gets dropped precisely at the interesting boundaries: the A2A handoff and the MCP tool call. Debugging a failed transaction becomes a needle hunt across four separate haystacks.
Complication · Security Reality

Agent prototypes ship with enterprise-blocking vulnerabilities

🎭Spoofable identity

Trusting raw headers like X-User-Email instead of verifying signed JWTs. Anyone can be anyone.

👑God-mode service accounts

Every agent sharing one over-privileged identity with unrestricted cross-project access.

📡Public backends

Internal microservices accepting internet traffic, guarded only by an API key at the perimeter.

🔑Passwords in env vars

Database credentials as plaintext environment variables instead of IAM database authentication.

From a security perspective, agent prototypes make dangerous compromises to get things working. They trust spoofable identity headers like X-User-Email sent from the browser, instead of cryptographically verifying signed JWTs. They give every agent one shared service account with broad privileges instead of least privilege per agent. They expose internal backend microservices to the public internet because cross-VPC networking feels too complex. And they embed database passwords in runtime environment variables. In an enterprise environment, any one of these is an immediate security block — all four together is a non-starter. A production agent architecture must guarantee that backends have zero public surface, that identity is cryptographically proven, and that credentials like database passwords simply do not exist.
Complication · Engineering Reality

Brittle coupling, unrepeatable environments, and docs that run out

🧩Brittle coupling

Every deploy mints a new engine ID. Hardcode it, and redeploying a specialist breaks the supervisor.

🌀Configuration drift

Console clicks and hardcoded project IDs: works in one project, fails in the next.

🗺️Undocumented edges

A2A streaming under ADK 2.3, SSE through a gateway, bidirectional PSC — no working references anywhere.

Finally, the day-to-day engineering reality. In Agent Engine, every deployment produces a new engine resource ID. If your supervisor hardcodes the specialist's engine ID, redeploying that specialist instantly breaks your supervisor. Setting up the infrastructure — cross-project Private Service Connect, IAM database auth, private DNS, proxies — involves dozens of interdependent steps; done manually through the console, you get drift, hardcoded project IDs, and environments that cannot be reproduced. And when you search for documentation on the genuinely hard parts — streaming tokens over A2A under ADK 2.3, or bidirectional Private Service Connect between Apigee and Cloud Run — the official docs run out. Teams spend months rediscovering the same solutions to the same integration traps.

So this is the central question of the webinar. Let's make the separation explicit, because it is the argument. Three projects, one concern each. The Apigee project is the governance plane: it holds the seven API proxies, the API products that define token quotas, and the developer apps and keys for every agent and every end user. The AI project runs the workload: four Agent Engines on GEAP, the backend-for-frontend behind IAP, the Firestore authorization database, Secret Manager — and it is also the single pane where every component's telemetry lands. The backend project simulates your existing line-of-business system: three microservices and a MySQL database that the AI project cannot reach directly at all. Why does this matter? Because the boundaries are enforced by project-level IAM and private networking, not by convention. The gateway is shared infrastructure with its own lifecycle; the business system stays untouched by AI concerns; and an auditor can reason about each project independently.

Credential split by direction: consumers present keys; Apigee mints Google tokens upstream. 7 proxies, one policy language.

Here is how Apigee functions as the system's central nervous system — this table is the whole governance story in five rows. The ai-agents proxy fronts the supervisor engine, translating client calls into authenticated Reasoning Engine requests. The aiplatform proxy fronts every model call the agents make — the agents never talk to models natively. The llm-stream proxy is the unified SSE endpoint for direct user-to-model chat, routing by model name to either Gemini or Claude while applying identical security and quota policy to both publishers. The mcp proxy governs tool discovery and execution. And the three management proxies front the backend microservices, minting short-lived Google ID tokens toward the internal load balancer. Note the credential split: southbound consumers always present an API key; northbound, Apigee mints the appropriate Google credential. No consumer ever holds a Google credential for something it shouldn't reach.
Answer · Governance Plane

Keys bound to identity, quotas enforced before the model runs

🪪Key ↔ identity binding

The key's owner_email must match the verified IAP identity. A stolen key 403s.

⛔Quotas at the edge

100k tokens/hour per agent · 10k/5 min per user — counted from real usage, rejected before the model call.

🔀Two publishers, one policy

Gemini and Claude behind the same endpoint, same keys, same quotas, same logging.

This is how the ungoverned-access problem dies. On screen is the Direct view of the demo — a user chatting with Gemini or Claude through the gateway on their own personal API key. When a request hits Apigee, the gateway doesn't just check that the key is valid. It verifies that the owner_email bound to that key matches the cryptographically verified IAP identity of the caller. Steal someone's key and it's useless — your authenticated email won't match, and the gateway returns a 403. On top of that, Apigee enforces LLM token quotas at the edge, before the request ever reaches a model: one hundred thousand tokens per hour for each agent, ten thousand tokens per five minutes for each end user, counted from actual usage. A looping agent or an over-eager user gets stopped at the gate — protecting both budget and backend. And notice the model picker: Gemini and Claude, two publishers, exactly one governance regime.

Rather than one monolithic agent with dozens of tools, capability is divided across three specialists: orders, products, customers. Each runs as its own independent engine, under its own dedicated service account, holding its own Apigee key delivered as a Secret Manager reference. And critically, each specialist sees only its own domain's MCP tools — the order agent cannot see customer tools, and the product agent cannot modify orders. This is deliberate, and it pays twice. First, security: it's least privilege at the agent level, with per-agent attribution and per-agent quotas at the gateway. Second, quality: a small tool surface keeps the model's tool selection deterministic — the fewer tools an agent can call, the more reliably it calls the right one. The specialists even run on different model publishers — some on Gemini, some on Claude — behind the same gateway with identical governance.
Answer · AI Plane

Streaming delegation over A2A — and discovery that heals itself

📡A2A token streaming (ADK 2.3)

  • RemoteA2aAgent proxies with a streaming client factory + SSE converter.
  • The UI reveals the handover the instant transfer_to_agent fires.
  • The exact hooks are documented — this is one of the undocumented edges, solved.

🔄Registry self-heal (~60s TTL)

  • Specialists auto-register in Agent Registry on deploy.
  • Every turn, the supervisor re-points to the newest live engine from a TTL cache.
  • Redeploy specialists all day — zero supervisor redeploys.

Brittle coupling — solved: the engine ID is resolved at runtime, never hardcoded.

Inter-agent communication rides on the A2A protocol, and two hard problems are solved here. First, streaming. The supervisor connects to specialists through RemoteA2aAgent proxies configured with a streaming client factory under ADK 2.3 — the exact client-factory and converter hooks are in the repo, because this is precisely one of those undocumented edges where teams burn weeks. The result: the UI shows the delegation the moment the supervisor emits the transfer, and the specialist's tokens stream back through the chain. Second, discovery. Every specialist auto-registers in Agent Registry when it deploys. The supervisor, on every turn, resolves each specialist to the newest live registered engine through a sixty-second TTL cache. So when you redeploy the order agent and it gets a brand-new engine ID, the supervisor picks it up within a minute — no restart, no redeploy, no coordination. The brittle-coupling complication from earlier is simply gone.
Answer · AI Plane · Security

Per-user agent access, fail-closed, revocable in one click

🔍Evaluated every turn

A before_agent_callback filters sub-agents against the user's Firestore ACL on every query — permission changes bite on the very next turn.

🚪Fail-closed by default

No Firestore record → no agent access. A before_tool_callback hard block is the unbypassable safety net.

🎛️Administered live

Admins edit user→agent bindings in the UI. No code change, no redeploy — and specialists are IAM-locked so the filter can't be bypassed.

Who may use which agent? That's a per-user, fail-closed access control system backed by Firestore. On every conversation turn, the supervisor takes the verified user email from the invocation context and reads that user's authorized agent list. If an employee is only entitled to the product catalog, the supervisor dynamically removes the order and customer specialists from its sub-agents for that request — the model literally cannot delegate to them. If no record exists for the user, the system fails closed: no agents at all. As a second layer, a before-tool callback hard-blocks any delegation that slips through. And because the specialist engines are IAM-locked to the supervisor's service account, there's no path around the filter. Administrators manage all of this live in the Admin view — a permission change takes effect on the user's very next message.
Answer · Security & Networking

Private by construction: verified identity in, minted tokens out, no passwords anywhere

🪪Verified IAP identity

The BFF verifies the signed IAP JWT — never the spoofable headers. That one verified email becomes the user ID, ACL subject, key owner, and log field.

🔒Bidirectional PSC

AI → Apigee over a PSC interface; Apigee → backend over a PSC service attachment. Traffic never leaves Google's backbone.

🛂IAM-only services

Backend Cloud Run accepts only Apigee's dedicated invoker SA, whose only power is run.invoker on those three services.

🚫🔑Passwordless database

Cloud SQL IAM auth: the runtime service account is the DB user. Zero passwords in the entire stack.

Now the four security holes from the complication, closed one by one. Spoofable identity? The BFF verifies the cryptographic signature of the IAP JWT assertion — never the plaintext headers — and that single verified email becomes the Agent Engine user ID, the ACL subject, the API key owner, and the user field on every log line. One identity, proven once, used everywhere. Public backends? There are none: both cross-project paths ride Private Service Connect — northbound from the agents into Apigee, southbound from Apigee into the backend's internal load balancer — so traffic never leaves Google's private backbone, and the backend project has no public surface at all. God-mode credentials? Backend services are IAM-locked to one dedicated invoker service account whose only permission is invoking those three services. And database passwords? They don't exist: Cloud SQL IAM authentication makes the runtime service account itself the database user. Nothing to leak, nothing to rotate.

Every entry carries the same W3C traceparent, minted at the BFF and propagated through IAP, the gateway, the engines, the A2A hops, and MCP. One filter = the whole transaction.

Here's the answer to opacity. When a user sends a message, the BFF mints a standard W3C traceparent. That identifier is passed to Apigee, injected into the Agent Engine session, forwarded across A2A metadata to the specialists — the hop where trace context normally dies — carried into the MCP server, and delivered to the backend microservices. Every component writes one structured entry per interaction into one of four named logs, all in the AI project, all on one canonical schema: the frontend log, the gateway log with token counts and quota state and a four-timestamp latency decomposition, the agent log, and the services log. The payoff is operational: filter Cloud Logging by one trace ID and you see the entire transaction, across all three projects, in order, with consistent latency fields. The four-haystack problem becomes a single query.

Answer · Replicability

The whole stack rebuilds from three empty projects — and proves it

📜Declared, not clicked

  • demo-environment.yaml — the only file naming projects, regions, admin identity.
  • Three manifests declare desired state; seven tools converge live state to them.
  • Same grammar everywhere: --check · --dry-run · confirm · --apply.

🧪Guard-railed by tests

  • Build fails on hardcoded project IDs — in code and docs.
  • Cross-manifest contracts verified: SAs, secrets, audiences.
  • Runs offline in seconds — no GCP credentials needed.

Auditing a live environment is one flag: --check prints an honest drift report — OK, DRIFT, MISSING — for every resource.

How do you deploy something this involved without human error — and how do you know an environment hasn't drifted since? Everything is declarative. One environment file names the three projects, the regions, and the admin identity — it is the only place those values exist. Three version-controlled manifests declare the desired state of the agents, the gateway, and the backend. Seven tools converge live cloud state to the manifests, and every tool speaks the same grammar: check gives you a read-only drift report, dry-run previews, bare execution asks for confirmation, apply runs unattended for CI. So auditing a live environment is literally one flag. And the repo defends its own replicability: guard tests fail the build if anyone commits a hardcoded project ID — in code or in documentation — and cross-check the manifests against each other so the service account one manifest creates matches the permissions another grants. Those tests run offline, in seconds, on every change.
