Governança de Sistemas Multiagente Empresariais no Google Cloud

Uma arquitetura de referência replicável com a Gemini Enterprise Agent Platform (GEAP), o protocolo A2A e o Apigee X

Repo  adk-apigee-multiagent-demo Formato  40 min + 2 demos ao vivo Licença  Apache 2.0
Sejam bem-vindos. Hoje vamos ver o que é realmente necessário para operar um sistema de IA multiagente em produção no Google Cloud. A maioria das demos no mundo da IA é construída dentro de um único projeto, na máquina de um desenvolvedor, com API keys pessoais e conexões diretas à internet. Isso é ótimo para prototipar, mas não é assim que o software empresarial funciona. No mundo real existem fronteiras de rede rígidas, requisitos de identidade, orçamentos de tokens e mandatos de auditoria. O que apresentamos hoje não é um brinquedo nem um diagrama conceitual. É uma implementação de referência completa e funcional que abrange três projetos separados do Google Cloud, governa cada interação com modelos e ferramentas através do Apigee, rastreia cada salto do navegador ao banco de dados com um único ID de correlação, e pode ser reconstruída do zero com manifestos declarativos. Tudo é open source. Vamos começar.
Situação

Chatbots de um único modelo estão evoluindo para redes multiagente coordenadas

🧭Decomposição do trabalho

Chatbots monolíticos de prompt único dão lugar a agentes supervisores que orquestram especialistas de domínio.

⚙️Ação autônoma

Especialistas agem sobre sistemas de negócio reais via Model Context Protocol (MCP) e APIs REST — eles não apenas geram texto.

🌐Operação distribuída

Uma única pergunta se espalha por engines, microsserviços e bancos de dados — cruzando fronteiras operacionais reais.

Nos últimos dois anos, a IA empresarial passou da sua primeira fase, que era principalmente de chatbots e assistentes de prompt único. Hoje as organizações constroem sistemas multiagente em que um supervisor delega tarefas especializadas a agentes de domínio: um especialista de pedidos, outro de perfis de cliente, outro de catálogo de produtos. Esses agentes não apenas geram texto; eles interagem com bancos de dados e microsserviços reais através do Model Context Protocol. E assim que você conecta agentes autônomos a sistemas de negócio em produção, a arquitetura muda completamente. Você não está mais administrando uma API simples de requisição e resposta. Está orquestrando um sistema distribuído de entidades semiautônomas que negociam tarefas, executam transações e consomem tokens de LLM caros em alta velocidade.
Situação

O Google Cloud já entrega os blocos de construção — o desafio é a fiação

🤖GEAP Agent Engine

Runtime gerenciado para agentes ADK na Gemini Enterprise Agent Platform (antiga Vertex AI): sessões, escalonamento, registro.

🔁Protocolo A2A

Padrão para descoberta de agentes, cartões de capacidades e streaming de tokens entre supervisor e especialistas.

🛡️Apigee X

O gateway empresarial: keys, cotas, analytics, políticas — comprovado em tráfego de APIs de missão crítica.

🗄️Cloud Run + SQL

Serviços de negócio serverless e MySQL gerenciado, conectados de forma privada via Private Service Connect.

Cada componente é maduro e está disponível hoje. O que falta é uma topologia governada e replicável que os una.

A boa notícia é que não precisamos inventar infraestrutura nova. O Google Cloud já oferece as peças fundamentais. A Gemini Enterprise Agent Platform — GEAP, que muitos de vocês conhecem pelo nome anterior, Vertex AI — nos dá o Agent Engine, um runtime serverless totalmente gerenciado para reasoning engines construído sobre o Agent Development Kit. O protocolo Agent-to-Agent, A2A, padroniza a comunicação e a negociação de capacidades entre supervisores e subagentes. Cloud Run e Cloud SQL fornecem computação escalável e persistência relacional segura. E o Apigee traz a camada de gestão de APIs que governa tráfego de missão crítica há décadas. Todos os componentes são maduros e estão disponíveis hoje. O verdadeiro desafio não é se as peças existem, mas como conectá-las numa topologia de produção segura, governada e operável. Essa fiação é exatamente o tema desta sessão.

O que construímos: um supervisor ao vivo delegando a especialistas — diante de vocês

Antes de falar de problemas, deixem-me ancorar isso em algo real. Este é o sistema que vamos dissecar hoje — não é uma maquete. O que vocês veem é a vista de chat com agentes da demo. A pergunta dos próximos minutos é: o que é preciso para operar isso com segurança numa empresa? Porque, do jeito que sai da caixa, um sistema assim traz quatro problemas sérios.
Complicação · Governança e Confiança

Acesso a modelos sem governança, e ninguém sabe dizer quem gastou os tokens

🕳️LLMs na sombra com credenciais amplas

  • Agentes chamam os modelos diretamente com keys estáticas de service accounts.
  • Sem identidade por usuário no perímetro do modelo, sem cotas.
  • Revogar um usuário significa quebrar o agente inteiro.

🧾Zero atribuição de custos

  • "Quem gastou os tokens, em qual modelo, através de qual agente?" — impossível responder.
  • O gasto é invisível até chegar a fatura mensal.
  • Responder exige construir um pipeline de logs sob medida.
Quando uma equipe empurra uma prova de conceito de agentes para produção, o primeiro muro é a governança e o controle financeiro. Nas montagens típicas, os agentes chamam a Vertex ou modelos de terceiros diretamente com credenciais amplas de service account ou API keys estáticas em variáveis de ambiente. Não há verificação de identidade por usuário na fronteira do modelo, não existe o conceito de cotas de tokens, e não há como revogar um único usuário sem quebrar o agente inteiro. Então chega a fatura mensal e ninguém consegue responder perguntas contábeis básicas: quem gastou cinquenta mil dólares em chamadas a modelos esta semana? Qual agente gerou esses tokens — o especialista de pedidos ou o supervisor? Qual usuário final provocou essa carga? Sem um gateway de governança no caminho, responder a essas perguntas exige construir e manter um pipeline sob medida só para interpretar e correlacionar logs de infraestrutura.
Complicação · Governança e Confiança

A delegação multi-salto transforma cada transação numa caixa-preta

Navegador→ BFF→ Supervisor→ Especialista→ MCP→ Cloud Run→ Cloud SQL

Onde aconteceu de fato o pico de 12 segundos de latência — ou o erro 500?

🗂️Silos dispersos

Logs espalhados entre projetos e fronteiras de serviço, cada um no seu próprio formato.

⏱️Sem relógio comum

Métricas de latência com formatos distintos e precisão inconsistente — nada fecha.

✂️Contexto de rastreamento quebrado

O traceparent se perde nos saltos A2A e nas chamadas de ferramentas MCP.

O segundo bloqueio é a opacidade. Numa arquitetura multiagente, uma consulta do usuário dispara uma cascata: o supervisor inspeciona o prompt, chama um modelo, delega via A2A ao agente de pedidos, que chama outro modelo, invoca uma ferramenta MCP, que atinge um microsserviço interno, que executa uma consulta SQL. Se essa requisição leva doze segundos ou falha com um erro 500, onde quebrou? Foi latência do modelo, uma consulta lenta, um timeout de rede ou overhead de orquestração? Nas arquiteturas padrão esses logs estão espalhados por serviços e projetos diferentes, em formatos diferentes, sem identificador de correlação comum — e o contexto de rastreamento que os uniria se perde justamente nas fronteiras interessantes: o salto A2A e a chamada da ferramenta MCP. Depurar uma transação com falha vira procurar uma agulha em quatro palheiros diferentes.
Complicação · Realidade de Segurança

Protótipos de agentes trazem vulnerabilidades que bloqueiam sua adoção

🎭Identidade falsificável

Confiar em headers crus como X-User-Email em vez de verificar JWTs assinados. Qualquer um pode ser qualquer um.

👑Service accounts todo-poderosas

Todos os agentes compartilhando uma identidade superprivilegiada com acesso ilimitado entre projetos.

📡Backends públicos

Microsserviços internos aceitando tráfego da internet, protegidos apenas por uma API key no perímetro.

🔑Senhas em variáveis de ambiente

Credenciais de banco de dados em texto puro em vez de autenticação IAM de banco de dados.

Do ponto de vista de segurança, protótipos de agentes fazem concessões perigosas para funcionar. Confiam em headers de identidade falsificáveis como X-User-Email enviados do navegador, em vez de verificar criptograficamente JWTs assinados. Dão a todos os agentes uma única service account compartilhada com privilégios amplos em vez de privilégio mínimo. Expõem microsserviços internos diretamente à internet porque a rede entre VPCs parece complexa demais. E guardam senhas de banco de dados em variáveis de ambiente. Num ambiente empresarial, uma única dessas vulnerabilidades é bloqueio imediato — as quatro juntas são um não definitivo. Uma arquitetura de agentes de produção precisa garantir que os backends não tenham superfície pública, que a identidade seja provada criptograficamente e que credenciais como senhas de banco simplesmente não existam.
Complicação · Realidade de Engenharia

Acoplamento frágil, ambientes irrepetíveis e documentação que acaba

🧩Acoplamento frágil

Cada deploy gera um novo engine ID. Se você o fixa no código, redesplegar um especialista quebra o supervisor.

🌀Drift de configuração

Cliques no console e IDs de projeto fixos no código: funciona num projeto, falha no próximo.

🗺️Bordas sem documentação

Streaming A2A no ADK 2.3, SSE por um gateway, PSC bidirecional — sem referências funcionais em lugar nenhum.

Por fim, a realidade de engenharia do dia a dia. No Agent Engine, cada deployment produz um novo ID de recurso. Se o seu supervisor fixa no código o engine ID do especialista, redesplegar esse especialista quebra o supervisor na hora. Montar a infraestrutura — Private Service Connect entre projetos, autenticação IAM de banco, DNS privado, proxies — envolve dezenas de passos interdependentes; feito manualmente no console, você ganha drift, IDs de projeto fixos e ambientes impossíveis de reproduzir. E quando você procura documentação das partes genuinamente difíceis — streaming de tokens via A2A no ADK 2.3, ou Private Service Connect bidirecional entre Apigee e Cloud Run — a documentação oficial acaba. As equipes passam meses redescobrindo as mesmas soluções para as mesmas armadilhas de integração.

Esta é a âncora arquitetural de toda a sessão — o diagrama completo e detalhado, e ele é navegável, então deixem-me percorrê-lo ao vivo. À esquerda, o projeto de IA: o navegador entra pelo Identity-Aware Proxy até o backend-for-frontend no Cloud Run, e aqui estão os quatro Agent Engines — o supervisor e os três especialistas — mais o Firestore para o ACL e o Secret Manager para as keys. Reparem nos dois links de Private Service Connect cruzando as fronteiras de projeto — para o norte, do projeto de IA ao Apigee, e para o sul, do Apigee ao backend. O projeto de IA não tem conectividade direta alguma com o backend; toda interação passa obrigatoriamente pelo plano de governança. Resposta · A Arquitetura

Três projetos, uma responsabilidade cada — separação auditável

🧠Projeto de IA

  • 4 Agent Engines — supervisor + 3 especialistas (GEAP)
  • BFF no Cloud Run, atrás do IAP — nunca público
  • ACL no Firestore · Secret Manager
  • Toda a telemetria aterrissa aqui — o painel único

🛡️Projeto do Apigee

  • Organização Apigee X — 7 proxies
  • API products com cotas de tokens de LLM
  • Apps e keys por usuário e por agente
  • Cunha tokens do Google upstream conforme a direção

🏪Projeto Backend

  • 3 microsserviços FastAPI no Cloud Run
  • Cloud SQL MySQL — autenticação IAM, sem senhas
  • ALB interno regional, roteado por caminho
  • Nenhuma superfície pública — só PSC
Vamos tornar a separação explícita, porque ela é o argumento. Três projetos, uma responsabilidade cada. O projeto do Apigee é o plano de governança: contém os sete proxies, os API products que definem as cotas de tokens, e os apps e credenciais de cada agente e cada usuário final. O projeto de IA executa a carga de trabalho: quatro Agent Engines na GEAP, o backend-for-frontend atrás do IAP, o banco de autorização no Firestore, o Secret Manager — e é também o painel único onde aterrissa a telemetria de todos os componentes. O projeto backend simula o seu sistema de negócio existente: três microsserviços e um banco MySQL que o projeto de IA não consegue alcançar diretamente de forma alguma. Por que isso importa? Porque as fronteiras são impostas por IAM em nível de projeto e rede privada, não por convenção. O gateway é infraestrutura compartilhada com ciclo de vida próprio; o sistema de negócio fica intocado pelas preocupações de IA; e um auditor pode raciocinar sobre cada projeto de forma independente.

Credenciais divididas por direção: consumidores apresentam keys; o Apigee cunha tokens do Google upstream. 7 proxies, uma única linguagem de políticas.

É assim que o Apigee funciona como sistema nervoso central — esta tabela é toda a história de governança em cinco linhas. O proxy ai-agents fica na frente do engine supervisor, traduzindo as chamadas do cliente em requisições autenticadas ao Reasoning Engine. O proxy aiplatform fica na frente de cada chamada a modelos feita pelos agentes — os agentes nunca falam com os modelos de forma nativa. O proxy llm-stream é o endpoint SSE unificado para chat direto usuário-modelo, roteando pelo nome do modelo para o Gemini ou o Claude enquanto aplica política idêntica de segurança e cotas aos dois publishers. O proxy mcp governa a descoberta e a execução de ferramentas. E os três proxies de management ficam na frente dos microsserviços do backend, cunhando Google ID tokens de curta duração para o balanceador interno. Reparem na divisão de credenciais: para o sul, os consumidores sempre apresentam uma API key; para o norte, o Apigee cunha a credencial do Google apropriada. Nenhum consumidor jamais possui uma credencial do Google para algo que não deveria alcançar.
Resposta · Plano de Governança

Keys vinculadas à identidade, cotas aplicadas antes de o modelo executar

🪪Vínculo key ↔ identidade

O owner_email da key precisa coincidir com a identidade IAP verificada. Uma key roubada recebe 403.

⛔Cotas na borda

100k tokens/hora por agente · 10k/5 min por usuário — contadas do uso real, rejeitadas antes da chamada ao modelo.

🔀Dois publishers, uma política

Gemini e Claude atrás do mesmo endpoint, mesmas keys, mesmas cotas, mesmo logging.

É assim que morre o problema do acesso sem governança. Na tela está a vista Direct da demo — um usuário conversando com o Gemini ou o Claude através do gateway com sua própria API key pessoal. Quando a requisição chega ao Apigee, o gateway não valida apenas a key. Ele verifica que o owner_email associado àquela key coincide com a identidade IAP verificada criptograficamente de quem chama. Se alguém rouba a sua key, ela é inútil — o e-mail autenticado do ladrão não vai coincidir, e o gateway devolve um 403. Além disso, o Apigee aplica cotas de tokens de LLM na borda, antes de a requisição chegar ao modelo: cem mil tokens por hora por agente, dez mil tokens por cinco minutos por usuário, contados sobre o uso real. Um agente em loop ou um usuário afoito é barrado na porta — protegendo orçamento e backend. E reparem no seletor de modelos: Gemini e Claude, dois publishers, exatamente um regime de governança.

Em vez de um agente monolítico com dezenas de ferramentas, a capacidade é dividida em três especialistas: pedidos, produtos e clientes. Cada um roda como engine independente, sob sua própria service account dedicada, com sua própria key do Apigee entregue como referência do Secret Manager. E, crucialmente, cada especialista vê apenas as ferramentas MCP do seu domínio — o agente de pedidos não enxerga ferramentas de clientes, e o de produtos não pode modificar pedidos. Isso é deliberado e paga em dobro. Primeiro, segurança: é privilégio mínimo em nível de agente, com atribuição e cotas por agente no gateway. Segundo, qualidade: uma superfície pequena de ferramentas mantém determinística a seleção de ferramentas do modelo — quanto menos ferramentas um agente pode chamar, mais confiavelmente ele chama a certa. Os especialistas inclusive rodam sobre publishers diferentes — uns no Gemini, outros no Claude — atrás do mesmo gateway com governança idêntica.
Resposta · Plano de IA

Delegação com streaming via A2A — e descoberta que se autorrepara

📡Streaming de tokens A2A (ADK 2.3)

  • Proxies RemoteA2aAgent com client factory de streaming + conversor SSE.
  • A UI revela a delegação no instante em que transfer_to_agent dispara.
  • Os hooks exatos estão documentados — uma das bordas sem documentação, resolvida.

🔄Autorreparação via Registry (TTL ~60s)

  • Especialistas se autorregistram no Agent Registry ao serem implantados.
  • A cada turno, o supervisor re-aponta para o engine vivo mais recente a partir de um cache com TTL.
  • Redisponibilize especialistas o dia todo — zero redeployments do supervisor.

Acoplamento frágil — resolvido: o engine ID é resolvido em tempo de execução, nunca fixado no código.

A comunicação entre agentes viaja sobre o protocolo A2A, e aqui dois problemas difíceis são resolvidos. Primeiro, o streaming. O supervisor se conecta aos especialistas por proxies RemoteA2aAgent configurados com um client factory de streaming no ADK 2.3 — os hooks exatos de client factory e conversor estão no repo, porque este é precisamente um daqueles pontos sem documentação em que as equipes queimam semanas. O resultado: a UI mostra a delegação no momento em que o supervisor emite a transferência, e os tokens do especialista fluem de volta pela cadeia. Segundo, a descoberta. Cada especialista se autorregistra no Agent Registry ao ser implantado. O supervisor, a cada turno, resolve cada especialista para o engine registrado mais recente por meio de um cache com TTL de sessenta segundos. Então, quando você redisponibiliza o agente de pedidos e ele ganha um engine ID novinho, o supervisor o adota em menos de um minuto — sem reiniciar, sem redesplegar, sem coordenação. A complicação do acoplamento frágil simplesmente desaparece.
Resposta · Plano de IA · Segurança

Acesso a agentes por usuário, fail-closed, revogável com um clique

🔍Avaliado a cada turno

Um before_agent_callback filtra os subagentes contra o ACL do usuário no Firestore em cada consulta — mudanças de permissão valem já no turno seguinte.

🚪Fail-closed por padrão

Sem registro no Firestore → nenhum acesso a agentes. Um before_tool_callback de bloqueio duro é a rede de segurança intransponível.

🎛️Administrado ao vivo

Admins editam os vínculos usuário→agente na UI. Sem mudança de código nem redeploy — e os especialistas são travados por IAM para que o filtro não possa ser contornado.

Quem pode usar qual agente? Isso é resolvido por um controle de acesso por usuário, fail-closed, apoiado no Firestore. A cada turno de conversa, o supervisor pega o e-mail verificado do usuário no contexto de invocação e lê sua lista de agentes autorizados. Se um funcionário só tem direito ao catálogo de produtos, o supervisor remove dinamicamente os especialistas de pedidos e clientes dos seus subagentes para aquela requisição — o modelo literalmente não consegue delegar a eles. Se não existe registro para o usuário, o sistema falha fechado: nenhum agente. Como segunda camada, um before-tool callback bloqueia na marra qualquer delegação que escape. E como os engines especialistas são travados por IAM à service account do supervisor, não há caminho para contornar o filtro. Os administradores gerenciam tudo isso ao vivo na vista Admin — uma mudança de permissão vale já na próxima mensagem do usuário.
Resposta · Segurança e Redes

Privado por construção: identidade verificada na entrada, tokens cunhados na saída, zero senhas

🪪Identidade IAP verificada

O BFF verifica o JWT assinado do IAP — nunca os headers falsificáveis. Esse único e-mail verificado vira o user ID, o sujeito do ACL, o dono da key e o campo de usuário em cada log.

🔒PSC bidirecional

IA → Apigee por uma interface PSC; Apigee → backend por um service attachment PSC. O tráfego nunca sai do backbone do Google.

🛂Serviços só-IAM

O Cloud Run do backend aceita apenas a SA invocadora dedicada do Apigee, cujo único poder é run.invoker sobre esses três serviços.

🚫🔑Banco de dados sem senhas

Autenticação IAM do Cloud SQL: a service account do runtime é o usuário do banco. Zero senhas em todo o stack.

Agora, os quatro buracos de segurança da complicação, fechados um a um. Identidade falsificável? O BFF verifica a assinatura criptográfica da asserção JWT do IAP — nunca os headers em texto puro — e esse único e-mail verificado se torna o user ID do Agent Engine, o sujeito do ACL, o dono da API key e o campo de usuário em cada linha de log. Uma identidade, provada uma vez, usada em todo lugar. Backends públicos? Não existem: os dois caminhos entre projetos viajam por Private Service Connect — para o norte, dos agentes ao Apigee; para o sul, do Apigee ao balanceador interno do backend — então o tráfego nunca sai do backbone privado do Google, e o projeto backend não tem superfície pública alguma. Credenciais todo-poderosas? Os serviços do backend são travados por IAM a uma única service account invocadora cuja única permissão é invocar esses três serviços. E senhas de banco? Não existem: a autenticação IAM do Cloud SQL faz da própria service account do runtime o usuário do banco. Nada para vazar, nada para rotacionar.

Cada componente escreve uma entrada estruturada por interação num de quatro logs nomeados, todos no projeto de IA, todos com um esquema canônico único: o log do frontend, o do gateway com contagens de tokens, estado de cota e uma decomposição de latência em quatro timestamps, o de agentes e o de serviços. O ganho é operacional: você filtra o Cloud Logging por um trace ID e vê a transação inteira, através dos três projetos, em ordem, com campos de latência consistentes. O problema dos quatro palheiros vira uma única consulta.

Resposta · Replicabilidade

O stack inteiro se reconstrói a partir de três projetos vazios — e prova isso

📜Declarado, não clicado

  • demo-environment.yaml — o único arquivo que nomeia projetos, regiões e identidade admin.
  • Três manifestos declaram o estado desejado; sete ferramentas convergem o estado real para eles.
  • A mesma gramática em todas: --check · --dry-run · confirmação · --apply.

🧪Blindado por testes

  • O build falha diante de IDs de projeto fixados no código — em código e em docs.
  • Contratos entre manifestos verificados: SAs, secrets, audiences.
  • Roda offline em segundos — sem credenciais do GCP.

Auditar um ambiente vivo é uma flag: --check imprime um relatório honesto de drift — OK, DRIFT, MISSING — para cada recurso.

Como implantar algo tão complexo sem erro humano — e como saber que um ambiente não derivou desde então? Tudo é declarativo. Um arquivo de ambiente nomeia os três projetos, as regiões e a identidade admin — é o único lugar onde esses valores existem. Três manifestos versionados declaram o estado desejado dos agentes, do gateway e do backend. Sete ferramentas convergem o estado real da nuvem para os manifestos, e todas falam a mesma gramática: check dá um relatório de drift somente-leitura, dry-run faz a prévia, a execução direta pede confirmação e apply roda sem supervisão para CI. Então auditar um ambiente vivo é literalmente uma flag. E o repo defende a própria replicabilidade: testes-guardião derrubam o build se alguém commitar um ID de projeto fixado — em código ou documentação — e verificam os manifestos entre si, de modo que a service account que um manifesto cria corresponda às permissões que outro concede. Esses testes rodam offline, em segundos, a cada mudança.
Resposta · Conclusões

Seis padrões que valem a pena levar — mesmo que você nunca implante a demo

1️⃣Streaming A2A, ADK 2.3

Os hooks funcionais de client factory + conversor SSE.

2️⃣Autorreparação via Registry

Redeployments de especialistas com zero acoplamento ao supervisor.

3️⃣Apigee como gateway de LLMs

Keys vinculadas à identidade, cotas de tokens, roteamento de dois publishers.

4️⃣Rastreamento de ponta a ponta

Um traceparent que sobrevive a IAP, A2A e MCP.

5️⃣Provisioners check/apply

Ferramentas convergentes e honestas com o drift, auditáveis com uma flag.

6️⃣Analytics de tokens sem ETL

Data Collectors → relatórios personalizados. Sem pipeline.

Mesmo que vocês nunca implantem este repositório de ponta a ponta, há seis padrões de nível de produção que podem levar diretamente. Um: os hooks exatos de client factory para subagentes A2A com streaming no ADK 2.3. Dois: a descoberta autorreparável em runtime que desacopla supervisores dos redeployments dos especialistas. Três: as configurações de proxies do Apigee para governar Gemini e Claude atrás de keys unificadas vinculadas à identidade e cotas de tokens. Quatro: a propagação de traces W3C de ponta a ponta que sobrevive aos saltos onde o contexto costuma morrer — IAP, A2A, MCP. Cinco: o modelo de ferramentas check-apply idempotentes com relatório honesto de drift. Seis: a analytics de tokens sem ETL a partir dos Data Collectors do gateway. Cada padrão é código documentado, testado e funcional no repo — desmontem e adaptem.
